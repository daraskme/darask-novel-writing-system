# 4スキルの連携と作品データ

既存作品を引き継ぐ、複数工程を進める、設定や台帳を更新するときに読む。単発の案出しや掌編では、必要な項目だけ使う。各スキルの資源ルートを `RESOURCE_DIR` とする。旧来の参照にある `SKILL_DIR` も、この共通資源ルートを指す。

## 依頼から担当を選ぶ

| 依頼 | 主担当 | 完了する範囲 |
|---|---|---|
| 世界観・人物・口調を作る、設定を整理する | ja-novel-bible | 設定資料・文体基準・必要な台帳更新 |
| あらすじ・章立て・展開を考える | ja-novel-plot | 全体・章の構成と、1回の生成で書ける小場面のプロット |
| 掌編・第N話・続きを書く | ja-novel-write | 原稿・軽量確認・必要な状態の引継ぎ |
| 原稿を診断・校正・推敲する | ja-novel-revise | 局所修正、結合した章や作品全体のつながり・重複・配分の調整 |

規模（掌編・短編・長編）は担当の中で扱う。`novel.toml` があるだけで連載執筆を始めない。「第3章の口調だけ確認」は revise、「第3章の展開案」は plot。複合依頼では必要な工程を続けるが、四つ全部を毎回実行しない。

担当は作業上の責任を表し、別エージェントの起動や別スキルの導入を必須にしない。単独導入でも、必要な後処理はこの資料と [長編運用](longform.md) の担当節に従って行える。ユーザーが求めた成果物を返す前に、機械的な引継ぎのための再依頼を求めない。意味が変わる未決事項があれば、その点だけ確認する。

## 基準と共有する正本

- ユーザーの明示指示・確定済みの決定を優先し、作品の設定・文体基準、既存原稿の声、スキルの既定値の順で補う。投稿先の規定は、その投稿先を選んだ依頼の条件として扱い、希望と両立しない場合は相違を示す。
- 作品データは作品フォルダに一組だけ置く。スキルのフォルダへ作品の設定を書き込まない。既存の保存場所を尊重し、小さな依頼に長編用のフォルダ一式を要求しない。
- `bible/` は未出を含む設定、`plan/`・`plot/` は今後の計画、`canon/` は本文に実際に出たこと。作者が知っている設定を、人物や読者も知っているとは扱わない。
- 承認された設定・文体基準は、生成された原稿に合わせて自動変更しない。本文が基準から外れたら、意図した変化か誤りかを確かめる。見本の文面を本文へ流用しない。
- 本文と索引が食い違ったら原稿を読み、索引の誤りを直す。本文と確定設定、または本文同士が矛盾する場合は、台帳を書き換えて解消したことにせず、依頼の修正範囲で裁定する。

## 更新の担当

| データ | 更新担当 | 他の担当から渡すもの |
|---|---|---|
| `bible/`、`style/style-sheet.md`、`style/glossary.toml`、設定に関わる `novel.toml` | bible | 新設定候補、口調・表記の変更案、適用する章 |
| `plan/logline.md`、`plan/structure.md`、`plot/beats/`、伏線の計画 | plot | 変更が必要な展開、本文で生じた未解決の問い |
| `work/scenes/` の生成区間、結合した `manuscript/` | 初稿は write、改稿・全体調整は revise | 確定条件、対象区間、修正を許された範囲 |
| `canon/`、伏線台帳の実績（状態・実際の章番号） | bible の台帳更新工程 | 採用された原稿、追加候補、改稿した範囲 |
| `reviews/` | revise または独立レビュー役 | 対象原稿と、役に必要な最小限の資料 |
| `plan/decisions.md`、`STATUS.md` | 作業中の担当 | 自分が行った決定・変更・残作業 |

同じ台帳への更新は一人ずつ行う。複数スキルが同じ事実を別々に追記しない。決定ログ・進捗は現在の内容を読んで該当部分だけ更新する。短編の `notes.md` は同じ区分を一枚にまとめてよい。

## 引き継ぐ情報

引継ぎは、元ファイルのパスと必要な差分を使う。長い設定資料を別ファイルに丸ごと複製しない。

| 引継ぎ | 必要な情報 |
|---|---|
| bible → plot | 世界の制約、人物の動機と関係、文体・ジャンルの約束、確定と未決の区別 |
| plot → write | 小場面ID・順序・目安字数、目的・障害・変化、開始/終了状態、次への引継ぎ、視点、人物と読者の知識、必須展開と自由部分 |
| write → revise | 原稿、今回の依頼、確認する観点、残す声や長所。読者役には設計意図を渡さない |
| write / revise → bible | 採用原稿、根拠箇所のある新事実候補、変わった人物・物・時間・呼称、未解決事項 |
| bible / revise → plot | 計画との差、今後への影響、追加・変更が必要な伏線候補 |

長編の執筆用には `build_context.py` で当該章の資料を束ねる。設定・ビート・本文・台帳を変えたら、その変更に影響されるパックを作り直す。

## 小場面で書き、全体を調整する

1回の生成では、800〜2,000字程度で書ける小場面を一つ扱う。これは運用上の目安で、モデル共通の能力上限や字数の下限ではない。長い同一場面は、行動や応答の自然な節目で複数の生成区間へ分ける。区間を分けるためだけに場所・時刻・視点を変えない。

plot は全体→章→小場面の順で必要な細かさまで設計し、各区間の目安字数の合計が章・作品の条件に収まるか確認する。短い繋ぎを800字へ水増しせず、複数の大きな出来事を一つの区間へ詰め込まない。既存の大きい場面カードは、執筆前に必要な範囲だけ分ければよい。

write は小場面を保存し、次の区間へ直前末尾と状態を渡す。各区間にあらすじ・再紹介・締めの感想を付けず、連続した本文として書く。章の完成形は小場面を順に結合して作り、結合のために長い本文を再生成しない。

revise は結合後の章、必要に応じて複数章・作品全体を見て、場面間のつながり、重複、時系列、声、山場と分量を調整する。まず全体で変える点を決め、実際の修正は影響する区間単位で行う。作品全体を一度に再出力することは要求しない。読者に何を伝えるか、出来事をどこへ置くかの変更はプロットへ戻し、確定設定の変更は設定管理へ戻す。

`work/scenes/` は組み立て用の原稿、`manuscript/chNNN.md` は採用された章本文。章を直接手直しした後に古い区間から再結合すると修正が消えるため、先にその変更を区間へ反映する。台帳の根拠には採用された章本文を使い、未結合の断片を完成章として扱わない。

## 追加設定と承認

本文で新しく作った事実は、根拠の引用を添えて `proposed` として記録する。ユーザーの原稿や明示指示に由来する事実、既に承認された変更は `confirmed` にできる。既存の承認や明確な委任がその変更を含むなら、同じ許可を取り直さない。承認の範囲が分からない追加設定は仮のまま残し、後続の設定を大きく積み重ねる前に確認する。

相談やプロットにしか出ていないことは、承認されてもまだ既出事実ではない。本文へ出るまでは設定・計画側で管理する。仮の事実を正式にするために本文を捏造しない。

## 確認と完了

- 設定の完了は基準と未決事項が分かること、プロットの完了は出来事と変化が分かること、執筆の完了は依頼の範囲を本文で満たすこと、推敲の完了は依頼された問題を確認・処置したこと。
- lint は確認候補を示す。FAIL も該当箇所と前後を読んで確かめ、実際の誤りだけ直す。意図した表現・誤検出は根拠を添えて残す。全警報をゼロにすることや文学的な点数を目標にしない。
- 字数・音数・個数・日付などを断定する箇所はツールで検算する。確認できない数は創作上の事実と混同せず、要確認として扱うか、依頼を保てる表現に直す。
- 次章へ進む前には、直前の採用原稿から章末状態と既出事実を更新する。推敲で既出事実が変わった場合も同じ。途中で終える依頼では `STATUS.md` に未反映の範囲と次の一手を残す。
- スキルの分割だけでは会話履歴は分離されない。独立した読者の反応が必要なときは [レビュー手順](review-protocol.md) に従い、別コンテキストへ必要な資料だけ渡す。

本文は本文だけのファイルへ保存し、検査結果・引継ぎ・設定候補は外に置く。外部投稿・送信は、ローカルでの執筆や形式変換とは別の行為として、依頼された範囲でのみ行う。
