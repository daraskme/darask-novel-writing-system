# プロット設計

誰が何をし、何が変わり、次に何を起こすかを、全体→章→1回の本文生成用の小場面へ具体化する。成果物は企画案、あらすじ、章構成、小場面カード、伏線計画。相談や設計の依頼から、そのまま物語本文の執筆・改稿へ進まない。

`SKILL_DIR` はこのファイルのディレクトリ。`RESOURCE_DIR` は、`SKILL_DIR` に `references/` があれば `SKILL_DIR`、それ以外は 2 階層上のリポジトリルート。参照資料中の `SKILL_DIR` は共通資源のルート `RESOURCE_DIR` と読み替える。

## 設計の範囲

- 作品全体、特定の章、一場面のどこまでを設計するかを依頼から決める。冒頭だけの依頼に全体の決着を足さない。
- 依頼の読後感、必須の出来事、結末、字数や媒体の条件を出発点にする。未指定なら具体案を作る。候補の比較が役立つときだけ、違いの分かる複数案を示す。
- 既存作品では、`STATUS.md` があれば作業位置を確認し、関係する設定、既出事実、現行の構成だけを読む。計画と実際の本文が異なるときは、どちらが現在の前提かを確かめる。
- 短い話の構成相談は数行のあらすじや場面カードでよい。全スキルの実行、長編用ファイル一式、全章の詳細ビートは必須にしない。
- 他工程への引継ぎや既存作品の計画・台帳更新では [共通の引継ぎと記録](references/workflow.md) を読む。

設計の詳細は [構成](references/structure.md) の必要な節を読む。ジャンル固有の期待を決める場合だけ [ジャンル](references/genres.md) の該当節を参照する。既存の設定・声の基準を変更する必要があれば、展開上の要件を明示して `ja-novel-bible` へ渡す。

長編の章ビートを作成・更新する場合は [長編運用](references/longform.md) の「plot：章設計」を読む。新規プロジェクトが必要な場合は同資料の「再開と初期化」を使う。

## 本文へ渡せる設計

| 単位 | 決めること | プロジェクトでの保存先 |
|---|---|---|
| 企画 | 主人公、きっかけ、求めるもの、障害や変化、読者に約束する体験 | `plan/logline.md`、`novel.toml` の `[contract] promise` |
| 全体構成 | 出来事の因果、主要な転換、結末、場面や章の比重 | `plan/structure.md` |
| 章 | 章全体の変化、必須の出来事、章末、字数配分 | `plot/beats/chNNN.toml` |
| 1回の生成用の小場面 | ID、字数目安、入口と出口の状態、目的・行動・変化、視点・知識、次への接続 | 章ビートの `[[scenes]]`。簡単な作品なら場面カードや `notes.md` |
| 伏線と開示 | 初出、触れ直し、回収予定、読者と人物の情報差 | `plot/foreshadowing.toml` |

- ビートを「信頼が深まる」のような機能だけで済ませず、それが起きる出来事にする。確定の展開と、本文で自由に選べる描写・言い回しを分ける。
- 世界の事実、各人物の認識、読者へ提示済みの情報を分ける。未提示の設定を読者の理解の前提にしない。人物の誤認や秘密を意図して使う場合は、いつ誰がどう知るかまで設計する。
- 三幕、起承転結、反転、敵役、各章の引きは選択肢であり、すべての作品に課さない。日常や恋愛の充足、語りの声、関係の変化も作品を進める力として扱う。
- 未来の出来事は計画として記録する。伏線を予定しただけで `planted`、回収を決めただけで `paid` にせず、本文に出た事実や実績を作らない。

形式を使うときは [章ビート](assets/templates/beat.toml)、[場面カード](assets/templates/scene-card.md)、[伏線台帳](assets/templates/foreshadowing.toml) の既存キー・IDを維持する。短い依頼ではこれらの全項目を埋める必要はない。

### 1回の生成へ渡す粒度

本文は一度に一つの小場面を書く想定で設計する。小場面は概ね 800〜2,000 字を目安とし、自然な区切りと必要な出来事を優先する。短い繋ぎを800字まで膨らませず、短い作品は一場面で完了してよい。出来事が多すぎる場合は、行動・応答・判断の節目で分ける。物語上は同じ場面を複数の生成区間へ分けてもよく、そのために時刻・場所・視点を不自然に変えない。

各 `[[scenes]]` には従来の `goal / conflict / change / knowledge` 等に加え、`id`、`target_chars`、`entry_state`、`exit_state`、`handoff` を記せる。新しいフィールドは任意で、既存ファイルにないことを形式違反にしない。新しく細分化する小場面には安定した章内 ID（`s01` 等）を付け、順序変更で振り直さない。詳しい形式と例は [構成の「場面と章ビート」](references/structure.md) を参照する。

`exit_state` と次の `entry_state` が繋がり、`handoff` に未完了の動作・返答・次の起点が分かるようにする。場面ごとの `target_chars` の合計を章・作品全体の字数条件と照合し、概算と厳密な上下限を区別する。

## 設計の確認と完了

依頼された出来事と結末があるか、人物の選択と小場面同士の接続がつながるか、解決に必要な情報や能力が唐突に現れないか、出来事と字数配分が無理なく収まるかを確認する。日付・年齢・移動・期限が筋に効く場合は計算し、本文側の読みやすさで隠さない。確認対象は変更した設計とその影響範囲でよい。生成後の原稿全体の繋がり・重複・文体・配分と大局的な調整は `ja-novel-revise` が担当する。

プロジェクトの ID や伏線を変更した場合は、必要に応じて `python "RESOURCE_DIR/scripts/ledger_lint.py" --project DIR` で参照切れを確認する。設計の未確定を既出事実として埋めて警報を消さない。詳しい引数は `--help` を参照する。

設計案と、執筆を左右する未決点を示して完了する。「このプロットで本文も書いて」など複合依頼の場合だけ、今回の小場面 ID・字数目安、守る展開、読者と人物の既知、入口・出口・次への接続を `ja-novel-write` に渡す。章や全体の見直しまで依頼されている場合は、組み上がった原稿と調整範囲を `ja-novel-revise` に渡す。担当の分離は別エージェントの起動を意味しない。別スキルが利用できなくても、必要な後処理は同梱の参照を使って完了し、機械的な引継ぎのための再依頼を求めない。
