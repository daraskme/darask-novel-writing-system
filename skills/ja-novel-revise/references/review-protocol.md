# レビュー運用（役割・集計・盲検比較・外部モデル）

いつ読むか: レビュー役を立てる直前。改稿版を前の版と比べるとき。ユーザーが別のモデルや人に原稿を見せたいと言ったとき。
いつ読まないか: 独立レビューや比較を要しない局所修正。`roles/` は実際に委任する役のファイルだけ使う。

`RESOURCE_DIR` は `references/` の親ディレクトリ、`PROJECT` は作品のルート。例に出てくる作品（定置網の修繕係・郁が、先代の修繕帳を借りに行く章）は書式を見せるための自作で、どの作品にも流用しない。

## 1. 誰が何を決めるか

lint は位置を出す。レビュー役は読んだ反応と診断を出す。どれを採り、どこを直すと宣言するかは検証担当が決める。書いた本人のコンテキストは評価に使わない。書いたときの意図が残っていて、紙面に無いものまで読み取ってしまう。

レビュー役に頼まないことが三つある。

| 頼まないこと | なぜ | 代わりに頼むこと |
|---|---|---|
| 点数・星・総合評価 | 同系モデルの採点は甘く、点を動かすことが改稿の目的にすり替わる | 問題がある箇所の引用と反応。相対比較は必要なときだけ行い、弱い箇所を無理に作らない |
| 修正後の文面 | その文が原稿に貼られて声が混ざり、レビュー役の癖が入る。設定を知らない役の文面は設定も壊す | 操作で書いた方向（「L71 の最終文を消して成立するか試す」）。校閲の一意な訂正だけは文面でよい |
| 機械が書いたように見えるか | 判定が安定しない。直す方向が「人のふり」になる。読者役にその疑いを渡した時点で読み方が変わる | 読者としての反応（やめたくなった行、読み返した行、先が読めた箇所） |

lint の警報と読者の反応は別の情報である。読者が楽しめても確かめた誤りは残さず、警報があっても作品の声に合う表現は機械的に直さない。

ユーザー本人が点数や講評を求めたときは、求めに応じてよい（ユーザーの明示指示が上にある）。ただしその点数を、改稿の採否や打ち切りの判断には使わない。

## 2. 役割と遮断表

| 役（ファイル） | 渡す | 渡さない | 渡さない理由 | 書ける場所 |
|---|---|---|---|---|
| 執筆 `writer.md` | 対象の小場面ビート、パック、直前の末尾と状態差分。改稿時は対象区間と短い指示書 | bible 全体、登場しない人物、レビューの生記録、lint の結果、ai-tells.md | 知っていることは書きたくなり、説明が本文に漏れる。避けたい語は見せると出やすくなる | `work/scenes/` の指定区間。委任元が結合する |
| 盲検読者 `reader.md` | 原稿。連載は既読範囲のあらすじ。ジャンル読者にはジャンル名と問い 1〜2 個 | 章ビート、bible、文体シート、ジャンル契約の文面、lint、会話の経緯、書き手が誰か | 意図を知ると「伝わった」と錯覚する。約束の文面を見せると、約束が本文だけから伝わったかを測れない | `reviews/` |
| 編集 `editor.md` | 結合原稿、区間 ID・入口/出口を含む章ビート、ログライン、文体シート、`novel.toml` の `[contract]`、読者レポート | facts・state・glossary の細目、lint、ai-tells.md | 台帳を見ると校閲を始め、カタログを見ると語を数え始める | `reviews/` |
| 校閲 `proofreader.md` | 原稿、`glossary.toml`、関連する既出事実、前章末の state、人物シートの設定・状況別口調、確定世界制約、文体シート、lint の N・C・G・M 群 | 未来の章ビート、読者レポート、未確定の設定案 | 既出と確定基準を照合し、未来の計画や好みを混ぜない | `reviews/`（検算スクリプトは `work/`） |
| 設定管理 `canon-keeper.md` | 確定原稿、章ビート、関連する `canon/` の事実と直前の状態、伏線台帳、glossary、決定ログ、登場人物のシート | `reviews/`、`work/` | 採られなかった指摘や旧版の内容が「事実」に混ざる | `canon/`、`plot/foreshadowing.toml`、`style/glossary.toml`、人物シートの「変化の記録」。作品の設定担当から委任された更新だけを行う |

役割資料を読むだけでは独立性は生じない。4 スキルの分割は機能の分割であり、同じ会話内でスキルや役名を切り替えても独立レビューにはならない。

意図は委任メッセージだけでなく、履歴の継承、親の要約、プロジェクト指示ファイルの自動読込でも渡る。盲検読者は、作者との会話履歴・親の要約・設計資料を継承しない新規コンテキストで起動する。自動読込も含め継承の有無を確かめられない場合は、「盲検」と呼ばず「情報を制限したレビュー」として扱う。

## 3. 編成を必要性で選ぶ

| 必要な検証 | 使う役 |
|---|---|
| 誤字、既出事実、呼称、数え上げの照合 | 校閲。局所修正なら担当自身の照合で足りる |
| 初見で何が伝わるか、読後感が届くか | 読者。ジャンルの楽しみを問う場合はジャンル読者 |
| 構成と本文のずれ、結合後の接続・重複・配分、場面の不足 | 編集。読者レポートを使うなら読者の後に |
| 大きな改稿で失った長所がないか | 前後比較。独立した判定が必要な場合は AB モード |

生成区間ごとに全体調整やレビューを起動しない。結合した章・複数章・全体のうち依頼に必要な範囲を評価し、短い一場面には義務化しない。字数や章番号だけで全役を必須にしない。必要な問いに答えられる最小の編成を選ぶ。読者と校閲は独立なら並列でよい。編集は読者レポートを使う場合だけ後にする。

感情の直球や決め台詞が売りの作品を抑制の基準で裁かせない。アーク全体の緩急を見たいときは、複数章を読者へ渡し、強く動かされた順と設計の山の位置を比べる。絶対的な点数を作る必要はない。

## 4. 委任メッセージ

汎用のサブエージェントに、役割ファイルのパスと入力のパスだけを渡す。手順や基準は役割ファイル側にあるので、メッセージに書き足さない。

```
最初に RESOURCE_DIR/references/roles/reader.md を読み、その指示に従ってください。
モード: 初読
対象原稿: PROJECT/manuscript/ch012.md
既読範囲のあらすじ: PROJECT/work/ch012.reader-recap.md
追加の問い: 次話を読むか
上の 2 ファイル以外、プロジェクト内のファイルを開かないでください。
出力先: PROJECT/reviews/ch012.r1.reader.md
```

役ごとに変わる行:

| 役 | モード | 入力として挙げるパス |
|---|---|---|
| reader | 初読 / ジャンル読者 / AB / 話者当て | 原稿（AB は 2 本、話者当ては台詞ファイル）、あらすじ。ジャンル読者には `ジャンル:` の 1 行と `追加の問い:` |
| editor | — | 原稿、`plot/beats/chNNN.toml`、`plan/logline.md`、`style/style-sheet.md`、`novel.toml`、読者レポート。短編は原稿、`notes.md`、読者レポート |
| proofreader | — | 原稿、`style/glossary.toml`、`work/chNNN.facts.md`（関連する既出事実の抜粋）、`canon/state/ch（N-1）.md`、`work/chNNN.lint.txt`、文体シート、人物シートの設定・状況別口調、確定世界制約 |
| writer | 初稿 / 改稿 | 小場面 ID とビート、`work/chNNN.pack.md`（短編は `notes.md`）、直前の末尾と状態差分。改稿は対象区間と `reviews/chNNN.rK.brief.md` も。保存先は `work/scenes/chNNN-s01.md` など |
| canon-keeper | 更新 / 承認反映 | 確定原稿、章ビート。承認反映は confirmed にする事実 ID の一覧 |

- 既読範囲のあらすじは、`canon/summaries/` の既出の章要約から親が作る。章ビートや bible から作らない（未出の情報が混ざる）。第 1 章と短編には要らない。
- 校閲に渡す `work/chNNN.facts.md` は、`canon/facts.jsonl` を登場人物 ID で絞った抜粋（proposed も含める）。`work/chNNN.lint.txt` は `novel_lint.py` を N・C・G・M 群に絞って（`--only`）実行した出力の保存。統計や語彙密度の警報は校閲に渡さない。fix / keep を決めるのは親だ。
- ジャンル読者に渡すのは、ジャンルの呼び名（読者が題名やタグから知りうる語。「ざまぁ短編」「日常の謎」）と、genres.md「ジャンル読者への問い」から選んだ 1〜2 問。`[contract]` の promise の文面、結末、仕掛けは渡さない。
- サブエージェントがファイルに書けない種類なら、返答を親が `reviews/` に保存する。要約せず全文を保存する。
- 並列: 読者と校閲は同時に出してよい。編集は読者レポートを入力にするので後。ジャンル読者は読者と同時。

## 5. 各役から返ってくるもの

**盲検読者**
1. 反応ログ。行番号と 15 字以内の引用つきで、やめたくなった行／読み返した行（分からなくて・良くて）／先が読めた箇所／誰の台詞か迷った箇所／説明されたと感じた行／取って付けたと感じた行。反応が無かった段落については何も書かれない。
2. 再話。本文を見返さずに 200 字程度で、何が起きたか、誰が何を望んでいるか、次に何が起きると思うか、いちばん残った一文。
3. 最も弱い段落を最大 3 つ、弱い順に。読む妨げが無ければ「妨げなし」とし、相対順位を頼まれた場合だけ比較する。弱さと改稿の要否は理由つきで別記する。
4. 理解できたかと、面白かったか・心に残ったかを分けた記録。
5. 追加の問いへの答え（あれば）。

点数、修正文、総評、書き手の推測は含まれない。含まれていたら集計でそこだけ捨てる。

**編集**: 冒頭で読み続けるかどうかと理由、気になる場面、§6 の書式による指摘と守る箇所。全体調整では接続・重複・配分の問題を区間 ID と短い修正方向で返す。方向だけで文面は無い。

**校閲**: §6 の書式で、表記・既出との矛盾・状態の連続・知識状態・呼称・世界制約・数え上げ。矛盾は「本文の引用」と「既出事実 ID か state の行」の対で示される。機械的に一意な訂正は修正後の文字列つき。

## 6. 指摘の書式と重大度

役にも、モデルにも、人にも依らない共通の書式。外部から持ち込まれた指摘もこの形に写してから裁く。

```
### E02 [S2] L60-66
引用: 「ほんなら、持っていかれ」
問題: 登志子が帳面を貸す気になった理由が紙面に無い。読者は理由を補えず、都合で動いたように読む
根拠: 読者レポートの再話に「なぜか貸してくれた」
方向: 説得の台詞を足すのでなく、郁が先に何かを差し出す行為を決め手にする
```

ID は役の頭文字（R 読者・E 編集・P 校閲・X 外部）＋連番。根拠は、本文の別の箇所、読者の反応、既出事実 ID、章ビートの項目、検算結果のどれか。校閲は「方向」の代わりに「訂正」（一意に決まる修正後の文字列）を書く。行番号は原稿ファイルの行（1 段落 1 行なので段落番号と同じ）。版が変わるとずれるので、位置の正本は引用のほうだ。

| 重大度 | 何か | 扱い |
|---|---|---|
| S1 | 読者が筋を追えない。既出との矛盾。視点の破れ。依頼で固定された intent・direction やジャンル契約に反する。投稿先の規定違反。数え上げの不一致 | 依頼範囲で訂正する。範囲外や根拠未確定なら報告 |
| S2 | 場面の目的が見えない。動機が飲み込めない。声が人物と合わない。説明の塊。`reader_should` の未達 | 依頼された改善への影響で優先する |
| S3 | 反復、リズム、語の選択 | 1 段落の中で済むものだけ |
| S4 | 好みが分かれる | 直さない。backlog に記録だけ |

重大度を最終的に付けるのは親。レビュー役が付けた重大度は提案として読む。

## 7. 集計して改稿指示書にする

1. **引用を原稿に当てる。** 各指摘の引用を Grep で探し、原稿に無い引用の指摘は捨てる。レビュー役は、内部でも外部でも、読んだ気になった文を引用として書くことがある。
2. **根拠の無い指摘を捨てる。** 引用も読者反応も事実 ID も伴わない「全体に描写が薄い」の類。
3. **契約に当てる。** ジャンル契約の `keep`、文体シートの例外宣言に当たる指摘は S4 に落とす（`emotion_naming = "direct"` の作品で感情の名指しを咎める指摘、`chapter_hook = "off"` の作品に引きを求める指摘）。
4. **読者の再話を `reader_should` と突き合わせる。** 短い再話の省略を即「未伝達」にしない。重要な欠落は、意図を教えない追加質問（「その時点で郁が知っていたことは何か」など）で確かめる。理解できたかと、面白かったか・心に残ったかは別に記録し、理解済みでも退屈という反応は残す。
5. **重ねる。** 同じ行・同じ現象を複数の役が別々に挙げていたら最優先。読者がやめたくなった行と編集の最弱場面が重なれば、そこが今回の中心になる。単独の指摘は重大度で採否を決める。
6. **採る方向を設定に当てる（省かない）。** レビュー役は設定の全体を知らずに提案する。採る予定の方向ごとに、コンテキストパック、前章末の state、関連する既出事実、呼称表、世界制約に当てて問う。その人物はその時点でそれを持っているか。知っているか。その場にいるか。その語はこの世界にあるか。声シートの話し方で言える内容か。
   例: 編集の E02 は、方向の末尾に「先代の形見の網針を差し出す、など」と具体物を添えてきた。state/ch011 では、網針は ch010 で親方の辰巳に預けたままになっている。郁は持っていない。方向を「何を差し出すかは、パックにある郁の持ち物から執筆側が選ぶ」に書き換えて採る。矛盾する方向をそのまま執筆役に渡すと、執筆役は指示を優先して既出を壊す。
7. **守る長所を必要な分だけ残す**。読者の「読み返した行（良くて）」「いちばん残った一文」を優先し、無ければ編集の候補から。ユーザーが触るなと言った文と決め台詞は数に入れず無条件で守る。決めずに改稿へ出すと、良かった破調が真っ先に均される。
8. **改稿指示書を書く。** 対象区間 ID・方向・守る表現・変更後の引継ぎを短くまとめる。全体調整でも書き直しは一区間ずつ行い、章全体の再生成を指示しない。件数上限を理由に依頼範囲を未完了にしない。執筆役に渡すのはこの 1 枚で、生のレビューは渡さない。生の記録は件数が多く、互いに食い違い、採らなかった指摘まで反映されてしまう。ユーザーが生の記録を見たいと言えば、そのまま見せてよい。
9. **残りを `reviews/backlog.md` へ。** S4 と、枠から溢れた S2・S3。ユーザーへの報告は依頼の観点に合わせる。

指摘が一つの場面の過半に及び、しかも視点の破れやビートの要約消化のような構造の問題なら、差分で繕わず場面単位で書き直す（手順は revision.md）。

改稿指示書の例:

```
# ch012 改稿指示書 r1

守る（触らない）
- L41「もう濡れてもいない盆だった。」読者・編集とも読み返した行に挙げた
- L52-57 郁が干し柿のへたを外すあいだのやりとり。台詞だけで二人が聞き分けられる
- 章末 L88 車内灯の下で切り口を見るところで終わること

直す（この 4 か所のほかは一字も動かさない）
1. [S1] L23 郁が登志子を「奥さん」と呼んでいる。ch009 で「登志子さん」に変わった（ch009-07）。戻す
2. [S2] L30-36 帳面の来歴を登志子が一息に話す。読者がやめたくなった箇所。この章で要るのは「三月が無い」に効く分だけ。残りは削るか、郁が訊いて登志子が答えない形に割る
3. [S2] L60-66 登志子が貸す気になった理由が伝わっていない（再話に「なぜか貸してくれた」）。登志子が応じる利害や価値観を本文で示す。郁の言葉か行為がその条件に届くようにし、物を使うならパックの持ち物から選ぶ
4. [S3] L71 の最終文を消し、その前の台詞で段落を終えられるか試す

見送り: L15 の喩え（S4、backlog）
```

## 8. 声の識別テスト

人物の声が混ざるという具体的な懸念や、声の識別確認を求められたときに使う。

1. 本文から台詞を 10〜15 本、話者が偏らないように抜く。内容で話者が割れる台詞（名乗り、職業の話、相手への呼びかけ）は外すか、固有名詞を伏せ字にする。
2. 人物ごとに見本を 2 本ずつ、別の確定章から取って A・B・C のラベルで示す（声シートの見本台詞を使ってもよい。その場合は「本文が声シートの声で書けているか」の検査になる）。
3. 同じ台詞で語尾マスク版も作る。一人称、終助詞、語尾の役割語を「＿」に置き換える。
4. `reader.md` の話者当てモードに、原文版と語尾マスク版を別々のサブエージェントで解かせる（同じ個体に両方見せると答えが漏れる）。
5. 読み方: 原文版でも迷いが多ければ、作品が求める識別性とのずれを調べる。原文版は当たるのに語尾マスク版で大きく落ちるなら、語尾だけで書き分けている。どちらも人物設定と本文を照合し、原稿の逸脱か設定側の不足かを分ける。設定変更は bible 担当へ候補として戻す。取り違えられた台詞に装飾的な発話タグを足して済ませない。

## 9. 盲検 A/B

大きな改稿で得失が不明なときに、前版との比較を使う。LLM の改稿は、指摘を全部反映した結果、角が取れて平らになることが多い。

1. 改稿に入る前に、現行版を `work/ch012.r1.md` として複製しておく（r1 は 1 周目のレビューにかけた版。2 周目の前は r2）。git の履歴があればそこから取り出してもよい。
2. 比較前に、今回改善したい読者体験を一つ決める。途中の章は継続意欲、最終章や完結掌編は結末の受け止め、喜劇は笑いの成立など、対象に合う問いを選ぶ。比べる 2 版を `work/ab/ch012.X.md` と `Y.md` に複製する。どちらを X にするかは `python -c "import random;print(random.choice('XY'))"` で決める。親が決めると「新版を後に置く」癖が出る。対応表は判定が返ってから `reviews/ch012.ab.md` に書く。
3. `reader.md` の AB モードで、§2 の遮断を満たす新規コンテキストに渡す。初読レビューをした個体は使わない。問うのは、選んだ読者体験にどちらがより届いたか。版の由来を伏せ、理由は両版の本文の引用で求める。どちらが改稿版かは推測させない。
4. 引用と差分を確認し、選ばれた理由が依頼の改善点に結び付くか判断する。新版が長所を失っていれば旧版に戻すか、改善した差分だけを残す。一人の好みを自動的な採否にしない。
5. 戻すときも、S1 の訂正（既出との矛盾、表記の FAIL、数え上げ）は旧版に差分で入れ直す。比較にかけているのは読者体験に関わる改稿であって、誤りの訂正ではない。
6. 判定の理由に挙がった引用が、2 版で同一の箇所ばかりなら、その判定は雑音として「差がない」に数える。

頻度は改稿の影響に合わせる。誤りの訂正だけなら省き、大きな場面の変更や読後感の比較が必要なときに使う。同系のモデルは整った版を選びやすいため、引用と作品の声を確認する。

## 10. 打ち切り

依頼された問題が解消し、変更に関係する確認が通ったら終了する。通常は 1〜2 周を見当とし、追加は具体的な未解決事項があるときだけ。好みの往復、同じ修正で改善がない状態、点数や警報数だけの改善を理由に続けない。

依頼範囲内の明確な誤りを、件数枠や読者投票を理由に放置しない。範囲外の重大な問題や未確認事項は、残件として根拠とともに返す。

## 11. 別コンテキストを使えないとき

同一コンテキストでは盲検も独立レビューも成立しない。原稿をファイルから再読し、依頼や設計で必要な内容を伝える行を指して確かめる。これは編集上の照合で、読者の反応を得たことにはならない。

修正版と旧版の変更箇所を並べ、得失と設定・声への影響を確認する。ユーザーに比較してもらうのは判断を依頼された場合や選択が必要な場合。別役が使えないだけで許可済みの修正を止めない。独立性が結果に関わる依頼では「同一コンテキストで確認」と明記する。

## 12. 外部モデルへの持ち出し

ユーザーが外部モデル・サービスへの送信を明示的に依頼または許可した範囲で行う。既に得た許可を未発表作という理由だけで再確認しない。許可のない外部送信はせず、内部でできる作業を進める。

送るのは対象原稿と役に必要な資料だけ。読者には既読範囲のあらすじ、校閲には該当する事実の抜粋を付ける。設計意図や採られなかったレビューを盲検読者へ渡さない。別サービスでも会話履歴や自動読込の継承がないことを確かめ、未確認なら盲検と呼ばない。

依頼の雛形は `assets/templates/external-review-request.md`。利用可能な正規のツールや CLI を使い、CLI の引数は実際の `--help` で確認する。モデル名はユーザーの指定か環境の既定を使う。失敗・空の返答をレビュー済みと数えず、無制限の再試行や未許可の送信先への切り替えをしない。

外部の指摘も内部と同じく、引用の実在、本文・設定との整合、依頼範囲で採否を決める。修正文をそのまま貼らず、必要な方向を原稿の声で実現する。点数や「AI が書いた」という判定を改稿の根拠にしない。

## 13. ファイルの置き場

```
reviews/ch012.r1.reader.md      読者（ジャンル読者は .genre.md）
reviews/ch012.r1.editor.md      編集
reviews/ch012.r1.proof.md       校閲
reviews/ch012.r1.ext-codex.md   外部の生の返答
reviews/ch012.r1.brief.md       改稿指示書（執筆役に渡すのはこれだけ）
reviews/ch012.ab.md             A/B の対応表と判定
reviews/backlog.md              見送った指摘
work/ch012.r1.md                1 周目のレビューにかけた版（改稿前の複製）
work/ab/  work/ext/             比較用・持ち出し用の複製
```

`r1` は周回。short は章番号を省く（`reviews/r1.reader.md`）。`reviews/` は残す。なぜそう直したかの記録になり、同じ指摘の往復を見つける材料になる。
