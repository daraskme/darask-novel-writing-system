# 構成 — 企画・章立て・伏線・反転・章の切り方

企画、あらすじ、章ビート、伏線計画を作るとき、または展開を組み直すときに必要な節だけ読む。全体→章→1回の生成用の小場面へ具体化し、設計自体の整合を確認する。本文は一度に一小場面を執筆し、組み上がった原稿全体の繋がり・重複・文体・配分や大局的な調整は検証・推敲が担当する。短い作品は一場面で完了してよい。

## 1. 設計の前提

依頼の対象が作品全体か、その一部かを決める。読後に何を味わいたいか、必須の出来事や結末、字数と媒体の条件を設計の軸にする。型へ合わせるためにユーザーの選んだ甘さ、苦さ、笑い、未解決の関係を変えない。

設計と本文の状態を混同しない。世界の設定、人物が知ること、読者へ既に示したこと、今後示す予定を区別する。前話が渡されていない場合に、都合のよい既出場面を作って前提にしない。

## 2. ログラインと企画

主人公が何をきっかけに何を求め、何に阻まれ、選択によって何が変わる話かを短くまとめる。対立中心の作品なら、引き下がったときに失うものも有効。日常や声で読ませる作品では、読者が得る体験を中心に置ける。

- 抽象的な案: 父の店を継いだ娘が、周囲と衝突しながら居場所を見つける。
- 出来事のある案: 船具店を継いだ娘が、帳簿を持ち去り得意先を断って回る叔父から店を取り戻そうとする。娘が店を守るほど、叔父が隠していた父の取引へ近づく。

プロジェクトでは企画を `plan/logline.md`、読者への約束を `novel.toml` の `[contract] promise` に残す。梗概を求められた場合は結末まで、紹介用のあらすじなら読者へ明かす範囲までにする。

企画を広げるときは、仕事や場所の具体的な制約、相容れない用事、物への異なる意味づけから考えられる。「もし〜、しかも〜」で向きの違う条件を組み合わせる方法も使える。最初の案を必ず捨てたり、毎回三案を作ったりする必要はない。

案を選ぶ相談では違いと読後感を示す。作成を任されているなら、明示条件に沿って具体化する。後から直しにくい重大な分岐だけを未決として扱い、章末型や技法の一覧を選ばせるために作業を止めない。

## 3. 構成の型

| 型 | 使える場面 | 型が役立つ問い |
|---|---|---|
| 三幕 | 長編の全体、目的を追う話 | 何で動き出し、どこで戻れなくなり、何を選んで終わるか |
| 起承転結 | 掌編、日常、怪談、各章 | 新しい事実や視点が、前の出来事の意味をどう変えるか |
| 序破急 | 山場や短編の速度 | 準備・展開・決着の速度がどう変わるか |
| 反復と変奏 | 連作、日常、関係を積む話 | 同じ行為の何が前回と違って見えるか |

型は診断に使い、割合や場面数を固定する規定にしない。「転」は対立の激化でなく、意味の変化でも成立する。

> 起: 引っ越しの朝、三年間話さなかった隣人が荷運びを手伝う。
> 承: 主人公は深夜の洗濯機の音に悩まされていたが、文句を言えなかった。
> 転: 隣人は、仕事から帰るのが深夜で、洗わなければ翌日の服がないと話す。
> 結: 主人公は「でも、うるさかったです」と言い、手伝ってくれた礼も言って去る。

理解が変わっても、許しや和解まで進む必要はない。指定された結末に必要な変化だけを選ぶ。

## 4. 場面と章ビート

章ビートは経過の要約ではなく、本文にする出来事を指定する。`goal / conflict / change` は、それぞれ目的、障害、場面の前後の変化として使う。穏やかな場面では、障害を無理に足さず、期待や関係の変化を示せる。

| 設計になりにくい記述 | 具体化する向き |
|---|---|
| 信頼を描く章 | 誰が何を任せ、相手がどう応じたか |
| 得意先を一日回る | その一日で決定的だった一件 |
| 帳簿を取り戻す | 何が妨げ、どの行動で状態が変わるか |
| 緊張が高まり、二人の関係が深まる | どの事実・行為・台詞が関係を動かすか |

連続した時間・場所・視点を場面の基本単位にすると、入口と出口の状態を追いやすい。複数視点や時間を飛ぶ作品では切替の単位を明示する。動きの少ない反応や内省の場面にも、理解・態度・決意の変化があれば意味がある。

`direction` には、省略したくないやり取り、読者に見せる物、守る演出を短く書く。本文の全台詞や比喩を先に固めず、必須の展開と自由な細部を分ける。伏線の設置だけが目的の場面は、別の用件へ重ねられるか考える。

### 1回の生成用の小場面

小場面は概ね 800〜2,000 字で本文にする単位として設計する。この幅は作業の目安で、下限ノルマでもモデルの能力についての保証でもない。短い繋ぎは短く残し、ユーザーが指定した字数や自然な区切りを優先する。

一つの小場面へ、発見・尋問・逃走・和解まで詰め込まない。やり取りが要約されそうなら、目的へ向かう行動と応答、判断、次の行動の節目で分ける。逆に、区切った結果として何も起きない断片が並ぶならまとめる。

物語上の一場面と生成単位は同一でなくてよい。同じ機械室で続く会話を二回に分ける場合、時刻・場所・視点を保ったまま、返答や動作が渡る位置で切る。生成の境界だからといって場面転換記号や再導入の説明を入れる必要はない。

既存の `[[scenes]]` を生成用の小場面にも使う。従来の `title / location / time / pov / characters / goal / conflict / change / anchor / knowledge / direction` は維持し、次のフィールドを任意で追加する。

| フィールド | 型 | 内容 |
|---|---|---|
| `id` | 文字列 | 章内で一意の `s01`、`s02` 等。外からは `ch003/s01` のように章と合わせて指す |
| `target_chars` | 正の整数 | この小場面の概算字数。未設定なら省略し、欠落を0字として合計しない |
| `entry_state` | 文字列 | 開始時点の所在・持ち物・関係・知識・進行中の動作など、今回効く状態 |
| `exit_state` | 文字列 | 終了時点の状態。次に何を済んだこととして扱えるか |
| `handoff` | 文字列 | 次の小場面 ID と受け渡す動作・返答・問い。終端なら、この章や作品で閉じることを記す |

新しく細分化する際は各小場面に ID を付ける。執筆順は配列の順で、IDは並べ替えや挿入のたびに振り直さない。未使用の ID を割り当て、過去の原稿や引継ぎが別の場面を指さないようにする。追加フィールドのない既存ビートも有効で、変更する範囲から必要な情報を補う。ID のない旧ビートに保存済み本文がある場合、並べ替え・挿入・削除より先に、現在の配列順に対応する `s01`、`s02` 等を `id` として明記して固定する。

例（既存の場面内容に追加する部分）:

```toml
[[scenes]]
id = "s01"
target_chars = 1000
title = "日誌を隠したままの点呼"
location = "L01"
time = "二月第二週の月曜、朝七時"
pov = "C01"
characters = ["C01", "C02"]
goal = "日誌を所長に見られずに書庫へ戻す"
conflict = "所長が機械室で日誌を探している"
change = "ちづるは日誌を持っていないと嘘をつく"
anchor = "所長の手の中の鍵束"
knowledge = "ちづるは筆跡を祖父のものだと考えている。所長は日誌が無いことだけを知る。読者には、鞄に日誌があることを示す"
entry_state = "ちづるは機械室へ入る。日誌は鞄の中。所長は机の前で日誌を探している"
exit_state = "日誌は鞄のまま。嘘を聞いた所長は、ちづるに点検を始めるよう指示した"
handoff = "s02: 指示への応答から、同じ機械室で点検を始める。入室や日誌の不在説明は繰り返さない"
direction = "返答を省略せず、鞄を手放せないまま点検へ移る事情を見せる"
```

`change` はこの区間で生じる変化、`exit_state` はその結果として次へ渡る状態を記す。次の `entry_state` は、前の `exit_state` を受け、間にある移動や時間経過が必要ならその接続を明記する。予定の状態を、まだ書かれていない原稿の実績にしない。

### 小場面から章・全体への字数配分

章の出来事と字数条件を、小場面へ大まかに配る。短い繋ぎは少なく、依頼の中心となるやり取りや反応には十分な幅を取る。すべて同じ字数に揃える必要はない。

| 小場面 | 主な仕事 | `target_chars` |
|---|---|---:|
| s01 | 日誌を隠し、所長へ嘘をつく | 1,000 |
| s02 | 点検中の応答で、嘘を維持する負担が現れる | 1,200 |
| s03 | 所長が去り、次の調査へ持ち出す物を決める短い繋ぎ | 400 |
| 合計 | この章の概算 | 2,600 |

合計は計算し、章の目標・全体の字数条件と照合する。概ねの指定なら過不足を見ながら配分を直す。厳密な上限・下限がある場合は、必要な内容が収まる設計かを確認する。`target_chars` が未設定の小場面がある合計は暫定とし、全体を配分済みと扱わない。

予算の見直しは出来事と配分の設計で行う。実際の原稿ができた後の字数・繋がり・重複・文体の調整は検証・推敲へ渡し、目標へ達するためだけに文を足さない。

### 知識状態と情報差

`knowledge` に、各人物の認識と読者への提示を分けて書く。認識の変化には知った経路を添える。

```text
開幕: 叔父は店の債務を知る。娘は知らない。読者にもまだ示していない。
中盤: 得意先の台詞で、娘は叔父が注文を断っていると知る。読者も同時に知る。
結末: 娘は父の机で融資担当者の名刺を見つける。債務の内容までは知らない。
```

設定資料に書いてあるだけの秘密は、人物や読者の知識にしない。逆に、既に提示した事実は説明し直す必要があるかを判断する。読者に先に分からせる、人物だけが誤解する等の差を狙う場合は、その根拠を設計する。

### 因果の受け渡し

章の `intent` に、前章末の何が起点となり、この章の変化が次へどう渡るかを書く。順番を自由に入れ替えられる同種の障害ばかりなら、情報、関係、時間、使える手段のいずれかを変えると進行が生まれる。

先の展開は必要な粒度で残す。長い連載では全体は粗く、直近の章を詳しくすると変更しやすい。全章の詳細設計を依頼された場合は、その範囲まで作る。

## 5. 感情強度の曲線

全章が同じくらいの山場だと、どこに重みがあるかが見えにくい。静かな章に関係を積み、後の別れや勝負に効かせるなど、出来事の大小と読者の感情の動きを分けて考える。

プロジェクトの `intensity` は 0〜100 の設計用の強さで、文学的品質の点数ではない。使う場合は `plan/structure.md` の章別値と揃える。機械が読者の感動を測定した値として扱わず、値に合わせて本文を水増ししない。簡単な作品なら、静かな区間・山場・反応の区間を言葉で区別するだけでよい。

山場が弱いときは、先に何を積んだかを見る。「二人は仲がよかった」だけでなく、何度も一緒にした仕事、相手のために取っておいた物など、失うものの具体性が後半に効く。同じ不幸や成功を増やすより、関係や選択の意味を変える。

## 6. 緊張台帳（伏線台帳）と事前登場

先を読みたくなる材料は、未解決の謎だけではない。約束した対面、人物の思い込み、読者の予測、声や日常の楽しさもある。全場面に危機や未回収の問いを残す必要はなく、連載の引きの強さは作品の契約に合わせる。

伏線を使う場合は、設置・触れ直し・回収の予定を対応させる。

- 設置に別の働きを持たせる。人物、情景、笑いとして自然に見える物が、後から意味を変えると目立ちすぎない。
- 間が空くなら、前と違う用件で同じ物や事実へ触れる。触れ直しの回数や間隔は連載の長さに合わせる。
- 回収には、読者が前の情報を思い出せる接点を置く。同じ物を別名で呼び続けて手がかりを消さない。
- 決定的な人物・能力・情報・規則は必要になる前に示す。既存連載なら使える既出の描写を探し、無かった過去を追加したことにしない。

例: 父が信用金庫の名入りタオルを何枚ももらっていたことを、最初は「物をもらうのが好きな人」の描写として置く。後で返済予定表が見つかると、通っていた理由が変わって見える。同じ事実が人物描写と手がかりの両方になる。

形式は `plot/foreshadowing.toml` の `id / content / status / planted_ch / payoff_plan_ch / payoff_ch / max_gap / note` を維持する。

| 状態 | 意味 |
|---|---|
| `planned` | 計画だけで、本文では未設置 |
| `planted` | 本文へ設置済み |
| `reminded` | 本文で触れ直した |
| `paid` | 本文で回収済み |
| `dropped` | 採用しない、または回収しないと決めた。理由を `note` に残す |

プロット担当は内容・回収予定・許容間隔を計画する。実際の設置・回収状態は、本文の出典を確認する台帳更新で反映する。予定の変更で `planted_ch` や `payoff_ch` の実績を上書きしない。廃案は行を消す代わりに理由を残し、意図して未解決にする問いは何を残すか明示する。

## 7. 反転

反転を使う場合は、前半の出来事を無効にするより、事実の意味や動機が変わる設計が扱いやすい。

| 同じ事実 | 最初の読み | 後から分かる動機 |
|---|---|---|
| 叔父が帳簿を持ち去る | 不正を隠している | 店の債務を娘に知らせたくない |
| 得意先へ注文を断る | 店を潰したい | 新しい掛けを作らせたくない |

表の読みでも真相でも通る細部を置き、表の読みでは説明できない違和感を開示につなぐ。視点人物の誤認は本人の認識として書けるが、語りの設計にない嘘を事実として断言して読者を欺かない。意図して信頼できない語り手を使う場合は、その方針を文体基準にも残す。

秘密を言わない理由も、人物の利害や状況から導く。単に一言言えば終わるのに誰も言わない展開は、長く引くほど不自然になりやすい。善意、恥、罪、相手への不信など、その人物に効く理由を選ぶ。

開示位置は、驚きとその後の反応にどれだけ時間を使うかで選ぶ。作品の一定割合へ置く義務はない。早い開示なら人物が追いつく過程を楽しめ、遅い開示なら意味の変化が主になる。反転を入れず、約束した快楽を積み上げて終える構成も選べる。

## 8. 動機の判定

人物が選択する場面では、「その人から見て何を得るか／失うか」を具体化する。「悪人だから」「筋の都合だから」で行動を決めると、展開が変わるたびに人物も変わってしまう。

仕事、命令、信念だけでも行動理由になりうるが、強い負担を負って続ける場合は責任、生活、忠誠、自己像等との結びつきを示す。両立できる利害なら交渉で解いてよい。対立を続ける必要があるなら、期限や別の責任など、今は合意できない理由を用意する。

人物の根拠自体が不足している場合は [人物設計](character.md) へ戻る。既存の確定した性格や声を、都合よく変えた計画として進めない。

## 9. 敵役と解決

解決は、それまでに示した能力・情報・関係・選択から生じるかを確認する。偶然を扱う作品もあるが、積み上げた選択を無意味にする救済は読者への約束を損ねやすい。

| 気をつける形 | 確かめること |
|---|---|
| 新能力や人脈で一気に解決 | それを使える根拠と限界を前に置いたか |
| 敵が終盤だけ油断する | その行動が既出の性格・情報から生まれるか |
| 説得一回で相手が翻意 | 相手が応じる利害や価値へ言葉が届いているか |
| 章末の危機が簡単に消える | 予告した出来事が実際の選択や結果につながるか |
| 指定された苦い結末を和らげる | ユーザーが求めた結果と読後感を保っているか |

犠牲や取り返しのつかない失敗は選択肢であり、解決の必須条件ではない。協働や準備が実って報われる結末も、その因果を見せれば成立する。

## 10. 冒頭

初めて読む範囲では、誰がどこで何をしているか、どの声で語るかを読者が掴める材料を置く。事件で始める以外にも、日常の違い、語り手の偏り、進行中の仕事が入口になる。

前提説明は、読者が必要とする時点までに分かる形にする。説明を全面禁止せず、行動や会話で置くか短く叙述するかを作品の声で選ぶ。未提示の設定を省きすぎても、用語や固有名詞を一度に並べても読者は迷う。

Web 連載の第1話なら題名やあらすじの約束へ早めに触れる設計が役立つが、固定の話数を規定にしない。静かな作品では、声や像が読む理由になっているかを見る。

## 11. 章末と結び

章末が物語世界の新しい状態を示すと、続きへの力が生まれる。語り手の無難な総括や「このときはまだ知らなかった」を毎回置くと、出来事の差が消えやすい。ただし回想体など、先を知る語り手の予告自体が声になっている作品は、その基準に従う。

章ビートの `ending_type` に使える型:

| 型 | 残るもの |
|---|---|
| 問い | 説明のつかない事実 |
| 反転 | 台詞や物証で変わった理解 |
| 決断 | 次に踏み出す行動 |
| 危機・期限 | 対応を迫る出来事や残り時間 |
| 約束 | 次の対面、勝負、楽しみな予定 |
| 余韻 | 出来事の区切りと、受け止める時間 |

`canon/endings.log` は同じ締め方の無自覚な反復を確かめる材料。直近と同じ型を機械的に禁止しない。`novel.toml` の `chapter_hook = required / optional / off` と場面の役割に合わせる。連載で危機を引いた場合は、次にその危機をどう受けるかまで考える。

作品全体の結びは、依頼された結果・反応・読後感を満たす。開いた結びでは読者が解釈できる材料を渡し、完結の充足を約束した作品では着地まで書ける構成にする。後日談や感情の言葉が必要かもその約束から決め、一律に削らない。

## 12. 執筆前のプロット検証

変更した設計と、その影響先を確認する。長編の全体構成では章をまたぐ対応、章ビートではその場面の因果を詳しく見る。掌編でも、数や知識状態が仕掛けの核なら確認する。

| 観点 | 確認すること |
|---|---|
| 依頼条件 | 必須の出来事、誰が誰へ何をするか、結果、対象範囲が揃っているか |
| 時間 | 日付、年齢、移動時間、期限が両立するか。筋に効く数は計算する |
| 知識 | 人物の判断と台詞に知った経路があるか。読者へ必要な前提を渡したか |
| 因果 | 目的と行動が結果へつながり、次の場面の起点になるか |
| 小場面の接続 | 安定した ID で対象を指せるか。前の `exit_state`・`handoff` と次の `entry_state` が一致するか |
| 生成の粒度 | 1回の本文で書く出来事が多すぎないか。分割によって時刻・場所・視点が不自然に変わっていないか |
| 字数配分 | 小場面の概算合計が章・全体の字数条件と両立し、未設定分を0字としていないか |
| 伏線 | 計画と実績を分け、`plant / touch / payoff` の ID が台帳と対応するか |
| 事前登場 | 解決の鍵となる物・人物・能力・規則に前の材料があるか |
| 世界と言葉 | 鍵となる語彙や比喩が時代・文化・話者の知識に収まるか |

IDや台帳の参照切れには `ledger_lint.py` を使える。警報を消すために未出の事実を捏造しない。設計の問題を本文の言い換えだけで隠さず、必要な範囲の計画を修正する。

計画変更時は旧案の残りを影響先で検索し、ログライン・構成・章ビート・伏線予定を揃える。実際の本文と基準設定はそれぞれの担当範囲として扱う。引継ぎと記録は [共通の引継ぎと記録](workflow.md)、長編の運用は [長編運用](longform.md) を参照する。
