# 長編・連載の運用

既存作品の章設計・執筆・改稿・台帳管理で、担当する節だけ読む。単発の相談や短い作品には一式を要求しない。担当の境界と共通原則は [workflow.md](workflow.md)、短編の運用は [short-pipeline.md](short-pipeline.md)。ここで `RESOURCE_DIR` は共通資源のルート、`PROJECT` は作品フォルダ、`N` は章番号、`NNN` は3桁表記を指す。

| 作業 | 読む節 |
|---|---|
| 新規作成・中断からの再開 | 1 保存形式、2 再開と初期化 |
| plot：章を設計する | 3 章設計 |
| write：本文を書く | 4 パックと執筆 |
| revise：検証・改稿する | 5 検証と改稿 |
| bible：既出事実を更新する | 6 台帳更新 |
| 設定変更・記録の修復 | 7 変更と復旧 |

## 1. 保存形式

既存の作品フォルダとファイル形式を引き続き使う。スキルごとに別の台帳を作らない。

```text
my-novel/
├── novel.toml                 作品の設定・文体・ジャンル契約
├── STATUS.md                  現在地、未反映の作業、次の一手
├── plan/
│   ├── logline.md             企画・あらすじ
│   ├── structure.md           全体構成・章の予定
│   └── decisions.md           変更と却下の記録
├── bible/
│   ├── world.md               世界の設定（未出を含む）
│   └── characters/C01-名前.md  人物と声、章をまたぐ変化
├── style/
│   ├── style-sheet.md         文体の基準と見本
│   ├── glossary.toml          表記・呼称・世界制約
│   └── lint.json              作品固有の検査設定
├── plot/
│   ├── beats/ch001.toml       章・場面の計画
│   └── foreshadowing.toml     伏線の計画と実績
├── canon/
│   ├── facts.jsonl            本文に出た事実と根拠
│   ├── summaries/ch001.md     章要約
│   ├── state/ch001.md         章末の状態
│   └── endings.log            実際の章頭・章末の型
├── manuscript/ch001.md        本文
├── work/                      パック、改稿前の版、一時ファイル
│   └── scenes/ch001-s01.md     小場面ごとに生成・保存する本文
└── reviews/                   指摘・改稿記録
```

- ID は人物 `C01`、場所 `L01`、伏線 `F001`。名前を変えても ID は保持する。
- 内部本文は1段落1行。ルビは `｜親文字《るび》`、傍点は `《《語》》`、場面転換は `＊` の行。既存原稿の表記変更は必要な範囲に限る。
- TOML は該当値だけ変え、既存のコメントや項目を保つ。雛形のコメント内は見本であり、作品の設定ではない。
- `facts.jsonl` の訂正は `supersedes` つきの追記。既存行を直接変えるのは承認を反映する `status` の更新だけ。
- 他の執筆ツールに設定の正本がある場合は、その場所を使う。必要な索引と引継ぎだけ作り、移行を強制しない。

## 2. 再開と初期化

既存作品では最初に `STATUS.md` を読み、依頼の対象章と必要な資料を選ぶ。ファイルの存在だけで執筆工程に切り替えない。進捗が無ければ対象の本文・設定・台帳から再開点を作る。編集直前には最新ファイルを確認し、ユーザーの手直しを戻さない。

新規の長編プロジェクトを求められた場合は、最初に作業する担当が雛形を一度だけ作る。

```text
python "RESOURCE_DIR/scripts/init_project.py" PROJECT --title 索道日誌 --profile entertainment --medium kakuyomu
python "RESOURCE_DIR/scripts/init_project.py" PROJECT --add-character C01 --name 鵜殿ちづる
python "RESOURCE_DIR/scripts/init_project.py" PROJECT --add-chapter 2 --chapter-title 木曜の写真
```

必要な質問は、依頼から分からず、結果の骨格を変えるものに絞る。企画・構成は plot、人物・世界・文体は bible の担当として必要な部分を埋める。一方の完了を待って全項目を順番に埋める方式にはしない。雛形を作ることと、内容が決まったことは区別する。

既存原稿を引き継ぐ場合は、対象章と連続性に必要な章から事実・状態を整理する。ユーザー原稿由来の事実は `confirmed` にできる。文体の基準はユーザーが選んだ既存原稿から取り、モデルが生成した本文で自動更新しない。

`STATUS.md` は短く保ち、現在地・次の一手・未決事項・台帳未反映の章・文体の基準・常設の指示を記す。「次の一手」は担当と対象が分かる形にする。

```text
- 現在地: ch004 初稿保存。軽量確認済み
- 次の一手: bible：ch004 の採用原稿から章要約と状態を更新する
- 台帳未反映の章: ch004
- 未決事項: 小椋の退職年は仮の設定
```

## 3. plot：章設計

前章末の状態、関連する既出事実、期限の近い伏線、却下済みの案を確認する。未反映の原稿があるなら先に必要な台帳を更新し、古い状態から次章を組まない。

全体構成は「その章で何が変わるか」の粒度で持ち、具体的なビートは近い章から作る。全章の細部を先に固定すると、本文の変化が計画へ反映されにくくなる。

本文生成用のビートは、1回800〜2,000字程度で書ける小場面に分ける。同じ場所・時刻・視点の長い場面を複数区間にしてよく、区切るためだけの場面転換は足さない。区間の分量は目安で、必要な出来事が短く書き切れれば水増ししない。

`plot/beats/chNNN.toml` では次を具体化する。詳しい作劇は [structure.md](structure.md)。

- `goal / conflict / change`：人物の目的、障害、終了時の変化。
- `direction`：誰が、どこで、何をして、どう反応されるか。抽象的な感情ラベルだけにしない。
- `knowledge`：場面ごとに誰が何を知り、誰が知らないか。読者の既知も区別する。
- `reader_should`：読者に伝わってほしいこと。レビュー後の照合に使い、読者役には渡さない。
- 伏線の設置・触れ直し・回収、視点、字数条件、開始と終了の状態。
- 任意の追加項目 `id / target_chars / entry_state / exit_state / handoff`：区間の識別子、目安字数、開始状態、終了状態、次の区間へ渡すこと。`[[scenes]]` の配列順で書き、並べ替えても ID は維持する。旧ビートに追加項目がなくても読み込める。

たとえば3,600字程度の章は、発見1,000字→相手との応酬1,600字→行動の決定1,000字のように、山場へ厚く配分する。均等分割は必要ない。章・作品の字数条件が厳密なら、区間予算の合計と実測の両方で確認する。

```text
抽象的: ちづるの疑念が深まり、小椋との会話に緊張が走る。
具体的: 番台越し。ちづるは日誌を見せず、壮吉が四月に山へ上がったかだけを訊く。
        小椋は釣り銭の皿を拭き、壮吉の足の話で躱す。ちづるが引き下がる前に、
        小椋のほうから、いま日誌を誰が書いているかを訊く。
```

台詞は原則として伝える内容を渡し、言い回しは本文担当に残す。ユーザーが固定した台詞は保持する。必須の出来事と自由に工夫できる部分を区別する。

`bible/world.md` の「詳細」はパックに入らない。その章に必要な情報はビートに要点を移す。計画を変えた場合だけ、影響するID・伏線・時系列を再確認する。

## 4. write：パックと執筆

章ビート、文体基準、前章末の状態が揃っているかを確認する。台帳の検査とパック生成は次を使う。

```text
python "RESOURCE_DIR/scripts/ledger_lint.py" --project PROJECT --chapter N
python "RESOURCE_DIR/scripts/build_context.py" --project PROJECT --chapter N
python "RESOURCE_DIR/scripts/build_context.py" --project PROJECT --chapter N --check
```

出力は `work/chNNN.pack.md`。執筆時はこのパックと、作風・場面に必要な技法資料を読む。設定資料や過去章をすべて読み直すことを前提にしない。パック内の `intent` や `reader_should` は設計意図であり、本文に貼る文ではない。

パックの必須部分は、執筆条件、章ビート、関連伏線、人物と呼称、文体、世界制約、前章末の状態。任意部分は、前章末尾、関連事実、決定ログ、過去章要約。予算超過時は任意部分が下位から省かれ、末尾に記録される。

- 必須情報の不足や必須部分だけでの予算超過では生成が止まる。先に不足を解消する。`--allow-missing` は不足を理解して進める場合だけ使い、欠落を確定事実で埋めない。
- パック末尾の省略情報を確認する。必要な情報が落ちていたら、予算や入力資料を調整する。
- パック作成後に原典を編集したら再生成する。`--check` は原典の変更を検知する。
- 伏線を回収する章では、設置した段落を追加で読むとよい。長い中断後は基準原稿や直近章を必要な範囲で読み、声と接続を取り戻す。
- Python がなければ同じ項目を手でまとめ、不足と未検査を明記する。

1回に書くのは一つの小場面。`work/scenes/chNNN-s01.md` のように章番号とビートの ID で保存する。ID のない旧ビートは配列順の `s01`、`s02` を使える。旧ビートを並べ替え・挿入・削除する前には、現在の代替 ID を各 `[[scenes]]` の `id` に明記し、保存済み本文との対応を固定する。途中から再開するときは保存済み区間を確認し、完了した区間を重ねて生成しない。

各区間の前に、文体の必須条件、直前の本文末尾、人物・物・知識の状態を確認する。同じ章の開始用パックだけに頼らず、直前区間で変わったことを次へ渡す。未指定の区間が長すぎる場合は、必要な範囲のビートを先に小分けにする。

区間ごとに導入や結びを作らず、前の文から続ける。字数条件があるときは途中でも実測し、後半を要約で消化しない。最後まで書けたら、次のツールで配列順に章本文へ結合する。

```text
python "RESOURCE_DIR/scripts/assemble_scenes.py" --project PROJECT --chapter N
```

出力は `manuscript/chNNN.md`。欠落・空の区間は結合せず、章を完成扱いにしない。章題や場面転換記号は自動追加されないので、物語上必要なものだけ区間本文へ含める。再結合に `--overwrite` を使う前に、章側の手直しが区間へ反映されているかを確認する。結合のために章全文をモデルへ再出力させない。

保存後は内容が実際に存在するかを確かめ、`novel_lint.py <原稿> --project PROJECT --only NCM` で表記・数え上げ・本文混入を軽量確認する。FAILも前後を読み、実際の誤りだけを直す。原稿全体の推敲は必要なときに §5 へ進む。

本文に無かった追加設定は、根拠の箇所とともに本文の外へ記録する。次章へ進む前には §6 の台帳更新を行う。単独導入でもこの後処理を実行できる。

## 5. revise：検証と改稿

依頼された観点と深さで [revision.md](revision.md) に従う。設定矛盾には本文と設定・既出事実、口調には人物・相手・状況・適用章の根拠を示す。本文を読まずに lint の抜粋だけで修正しない。

小場面を結合した後の全体調整は、この担当で行う。章では区間間の重複した導入・説明・結び、状態の食い違い、話し方、緩急、字数配分を確認する。複数章・全体では、出来事の因果、伏線の設置と回収、人物の変化、山場の位置を俯瞰してから、必要な本文箇所を読む。全体把握と長文の一括再生成を同じ作業にしない。

修正方針を対象の ID とともにまとめ、影響する小場面を直して再結合する。短い橋渡しの追加や再配置は全体調整の範囲で行えるが、人物の根幹や指定された結末を無断で変更しない。章本文を直接直した場合は、後で再結合する前に区間ファイルへ反映する。未導入の区間管理を既存原稿の局所推敲だけのために作り直す必要はない。

読者の反応が必要なら [review-protocol.md](review-protocol.md)。読者へ渡す既読のあらすじは `canon/summaries/` の【出来事】から作り、未出の計画を混ぜない。スキルを分けただけで独立レビューになったとは扱わない。

改稿前の版を保存し、変更後に元の長所・声・意味を失っていないか比較する。独立したA/B比較は、大きな変更で判断が難しい場合に使える。通常の局所修正に必須化しない。

採用した改稿で事実・時刻・持ち物・関係・知識が変わったら、該当章の台帳と後続章への影響を §6〜§7 で反映する。台帳のみの誤りなら本文を変えない。診断のみの依頼では変更せず、必要な修正先を示す。

## 6. bible：台帳更新

採用された原稿を読み、事実→要約→状態→伏線実績→呼称と人物変化→章頭末記録の順を目安に更新する。同じ原稿を複数担当で重複登録しない。次の章に必要な状態が記録されればよく、作中の全動作を事実台帳へ写さない。

### 既出事実

`canon/facts.jsonl` には、後の章で矛盾しうる数値、関係、知識、特徴、約束などを登録する。根拠 `quote` を本文から短く引く。設定やビートにしかないことは登録しない。新しい即興は `proposed`、ユーザー原稿・指示・承認に由来する確定事項は `confirmed`。既存の承認を取り直さない。

```json
{"id":"ch004-01","ch":4,"fact":"壮吉は数字の7に短い横棒を入れて書く","chars":["C01","C04"],"status":"proposed","quote":"七の腹に、短い横棒が一本"}
```

執筆担当が申告した候補と照合する。既存事実は再登録せず、訂正は新しいIDと `supersedes` で行う。承認前の候補も状態の再現に必要なら使えるが、その上に新たな確定設定を積み重ねない。

### 章要約と章末状態

章要約は `canon/summaries/chNNN.md` に【出来事】【状態変化】【未解決】で書く。固有名・数値・誰が何を知ったかを残し、先の計画や解釈だけの要約にしない。【出来事】の最初の一文で章の出来事が分かるようにする。

```text
【出来事】ちづるは平成21年度と30年度の日誌を見比べたあと、小椋を訪ね、
壮吉が四月に山へ上がったかを訊く。小椋は答えず、いま日誌を書く人を問い返す。
【状態変化】小椋はちづるが壮吉の四月を調べていると知った。日誌の持ち出しは知らない。
【未解決】四月十九日の欄を書いたのは誰か。小椋はなぜ書き手を気にするのか。
```

章末状態 `canon/state/chNNN.md` には作中日時、所在、怪我、持ち物、関係、知ったこと・まだ知らないこと、場所や物の状態を書く。パックに入るのは前章末の状態だけなので、継続中の怪我や持ち出した物は変化がなくても引き継ぐ。日時・曜日・日数の断定は計算で確かめる。

```text
- 作中日時: 二月第二週の火曜、夜
### C01 鵜殿ちづる
- 所在: 下の湯の番台の前
- 体調・怪我: 右手人差し指の切り傷（ch003から）
- 持ち物: 平成30年度の日誌は鞄の中。平成21年度は書庫に戻した
- 新たに知ったこと: 小椋は火・木・土に下の湯にいる
- まだ知らないこと: 予備鍵が一本足りないこと
```

### 伏線・呼称・人物変化

- 伏線の計画は plot、本文での設置・触れ直し・回収の実績は bible。ビートにあっても本文に出ていなければ、実績を進めない。予期しない問いは候補として plot に渡し、勝手に正式な伏線へ登録しない。
- 用語・呼称は `style/glossary.toml` が正本。変更は旧項目を残し、`[[address]]` に `from_ch` を付けて追記する。
- 人物シートの本体は開始時点の設計。「変化の記録」へ本文で起きた変更だけを `- ch005〜: 内容` の箇条書きで追加する。表にしない。予定は構成やビートに置く。
- `build_context.py` は書く章より前に起きた変化を反映する。たとえば ch005 内で呼称が変わるなら、ch005 の開始は旧呼称、途中の変化はビート、ch006 以降は記録された新呼称を使う。過去章を直す際も当該章のパックを作り直す。

`canon/endings.log` は `ch004 | 頭: 物 | 末: 問い` のように1章1行、短い型名で記す。計画と違えば実際の型を使う。型の反復は診断材料であり、交互配置のために改稿しない。

最後に `ledger_lint.py` で更新に関わる参照・欠落を確認し、`STATUS.md` の未反映範囲と次の一手を更新する。新設定の承認が必要なときは、既に決まっていることを除いて短くまとめる。

## 7. 変更と復旧

`plan/decisions.md` は追記式。見出しは `## D番号 日付 種別`、種別は `change / reject / note`、本文は「内容・理由・影響」。影響には章・人物・伏線IDを含める。却下した案は再提案を防ぐために残す。

```text
## D004 2026-09-20 change
- 内容: 小椋の退職を平成24年から平成27年へ変更
- 理由: 壮吉が晩年に山へ通った時期と在職期間を重ねる。ユーザー指示
- 影響: C03, C04, ch004
```

設定や原稿を変更したら、関連する事実・章・伏線を検索し、依頼の範囲で原稿・要約・状態を更新する。事実の訂正は次の形式で追記する。

```json
{"id":"ch004-04","ch":4,"fact":"小椋保は平成27年に退職","chars":["C03"],"status":"confirmed","supersedes":"ch004-02","quote":"二十七年の春に、鍵を返した"}
```

公開済み本文と矛盾する変更は、どこまで直すかを依頼・既存の許可から判断する。許可がなければ影響と選択肢を示す。辻褄合わせの新設定を勝手に増やさない。更新後は影響するパックを作り直す。

再開時に本文だけあって台帳が無ければ台帳更新から、台帳まであれば次の依頼工程から進む。部分原稿は完成済みと扱わない。後続章がある過去章の修正では、変わった事実がどこまで伝播するかを確認する。

前の版は `work/` や既存の履歴管理に残す。git を使う依頼があればその方針に従う。ローカルで原稿を直すことと、外部への投稿・push は分けて扱う。
